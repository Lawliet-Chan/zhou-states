# 客户端与服务器的通信

游戏状态只在服务器上（权威服务器）。客户端（Godot）用 WebSocket 连上服务器，收发 JSON 文本消息，每条消息都有 `type` 字段。

启动服务器：

```
cargo run -p zhou-server -- --addr 127.0.0.1:7878 --turn-seconds 0
```

- 有存档（默认 `saves/world.json`）就读存档，没有就从剧本开局；每回合结算后自动存档
- `--turn-seconds`：每回合的时限，到时间就结算；0 为只等在线的人都点「结束回合」

## 客户端发的消息

| type | 字段 | 说明 |
|---|---|---|
| `login` | `player`：人物 id | 以这个人物的身份登录（暂时没有密码） |
| `command` | `req`：客户端自己编的号；`command`：指令 | 下指令，指令的格式就是 `zhou_core::Command` 的 JSON，例如 `{"type":"march_army","army":12,"to":{"q":3,"r":1}}` |
| `view` | | 要一份眼下的情况 |
| `end_turn` | `ready`：默认 true，false 为取消 | 点「结束回合」 |

## 服务器发的消息

| type | 字段 | 什么时候发 |
|---|---|---|
| `welcome` | `player`、`config`、`view`、`last_turn` | 登录成功。`config` 是全部数值配置，`view` 是眼下的情况，`last_turn` 是上一回合的报告（刚开局时为 null） |
| `result` | `req`、`ok`、`ids`、`error` | 指令的结果，只发给下指令的人。`ids` 是新建出来的东西（新军队、新战争……），`error` 是失败的原因 |
| `view` | `view` | 有人下了指令、情况有变时，发给所有在线的人，各自只含自己看得到的部分 |
| `waiting` | `ready`、`waiting` | 谁点了结束回合、还在等谁 |
| `turn_ended` | `report` | 回合结算完，发这一回合的报告，之后就是新回合 |
| `error` | `message` | 消息看不懂、没登录就下指令等 |

`view` 和 `report` 都是 `PlayerReport`（见 `crates/zhou-core/src/view.rs`），只含这个人看得到的东西（战争迷雾）：自己的城的全部内情、自己的军队、视野里和记得的别人的军队与城的外观、和他有关或者他看得到的消息。报告里还有 `offers`（别人给他的、还没答复的管理任命和封授）和 `deals`（他提出的和别人向他提出的交易，当回合有效）。回合中的 `view` 里，`events` 是这一回合到目前为止发生的事；城的工作记录（`jobs`）只在回合结算的报告里有。

## 配置

`welcome` 里的 `config` 就是 `config/balance.toml` 转成的 JSON，字段名、结构和 toml 一样（见 `crates/zhou-core/src/config.rs`），只在登录时发一次。报告里的物品、兵种、地形、建筑等都用 key 表示，前端拿 key 去配置里查中文名和数值，例如物品类别 `ritual` → `config.categories.ritual`（「礼器」），兵种 `cavalry` → `config.units.cavalry.name`，身份 `nan` → `config.ranks.nan`（「男」）。前端不要自己再抄一份数值。

## 数值

所有数值都是整数，没有浮点数。带小数的量（物资、比例、倍率、愉悦度、风评……）以千分之一为单位：1.5 存为 `1500`，25% 存为 `250`。人数、回合数、id 等本来就是整数的照常。报告、配置、指令都是这样，客户端发小数服务器不认（回 `error`）。客户端显示时再换算。

## 坐标

六边形格子用轴向坐标 `{"q": .., "r": ..}`。地图按「奇数行向右缩进半格」排，换算成行列：`col = q + (r - (r & 1)) / 2`，`row = r`。

## 回合

和文明系列的同时回合一样：大家在同一个回合里各自下指令，指令立刻生效；在线的人都点了结束回合（或者到了时限）就结算。不在线的人不会拖住回合。

## 还没做

- 登录密码、账号
- 消息还是中文文本（带着谁能看到），没有拆成结构化的事件类型

## 军队驻守状态

己方军队报告的 `on_wall` 表示是否驻守城墙。前端据此仅显示「驻守城墙」或「撤离城墙」，通过 `man_wall` 指令切换，结果以服务器刷新为准。

## 行军的通行权确认

普通行军仍发送 `march_army`、`force: false`。服务器按实际路线检查通行权，若需硬闯，返回 `march_confirmation`（`req`、`cities` 城名列表），本次指令不移动、不宣战。客户端显示「无权经过，硬闯等于宣战」；取消不发指令，确认后重发同一目的地并设 `force: true`。有通行权或已经交战的城邑不要求确认，城墙等阻挡仍由服务器校验。

## 占领

远程攻击只能破坏城防。城墙已破、守军已清除、城中心血量归零后，军队实际进入治所格才触发占领；近战攻打治所后满足条件会进入该格，行军进入已失守的治所也能占领。
